# BJ-11: Sign in with an emailed code so it works in the installed app

## Brief

<!-- Gate 1. Small: what, why, done-when, and the test that should fail first. Full: see gw-brief. -->
Intent: the owner installed the app on an iPhone and could not sign in there. The emailed magic link opens in Safari, which has separate storage from the home-screen app, so the installed app never receives the session. Let the reader sign in inside the app by typing the code from the email. Repeated attempts also hit the email rate limit with no explanation; say so plainly.

In scope:
- After the reader asks for a sign-in email, the account panel keeps their address and shows a labeled field for the code from that email, with a Sign in button. Verify with supabase-js auth.verifyOtp({ email, token, type: "email" }). The link in the same email keeps working for browsers.
- Accept codes of 6 to 10 digits (the length is a Supabase project setting); strip spaces; inputmode numeric, autocomplete one-time-code.
- Clear, calm messages: wrong or expired code; too many emails requested (Supabase returns a rate-limit error, status 429 or code over_email_send_rate_limit): say an email was sent recently and to wait before asking for another, without losing the code field; offline.
- A "Send a new code" action that is disabled while a send is in flight, and "Use a different email".
- Copy explains in one sentence that on a phone's home-screen app the code is the way in, because the link opens in the browser.
- README: the Supabase email templates (Magic Link and Confirm signup) must include the code, {{ .Token }}, alongside the link; the built-in email service allows only a few emails an hour and a custom SMTP sender lifts that.
- Keep the existing focus handling and accessibility of the account panel (status paragraph, focus moves, aria-busy, 44px targets, no horizontal scroll at 360px) and the sage design rules (no cards, pills or boxes; plain rectangular button; text links).

Out of scope: Google sign-in changes, the sync engine, anything outside the account panel, session module and README.

Acceptance: unit or component tests cover requesting a code, verifying a good code, a wrong code, the rate-limit message and resending, with a fake client; existing tests still pass; lint, typecheck, unit tests, build and Playwright pass with no environment variables.
