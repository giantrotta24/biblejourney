# BJ-12: Study assistant only for accounts the owner enables

## Brief

<!-- Gate 1. Small: what, why, done-when, and the test that should fail first. Full: see gw-brief. -->
Intent: sign-up is open and strangers are already finding the app. The study assistant spends the owner's Anthropic credit, so it must work only for accounts the owner has explicitly enabled, one by one, from the database. Everything else in the app stays open to any signed-in or signed-out reader.

In scope:
- New migration supabase/migrations/20261114020000_assistant_access.sql (do not edit earlier migrations; they have been applied): table public.assistant_access (user_id uuid primary key references auth.users on delete cascade, granted_at timestamptz not null default now(), note text). RLS enabled with NO policies; revoke all from anon and authenticated; grant to service_role. A signed-in user must not be able to read, insert or update it, so a reader cannot enable themselves (the own-rows policies on profiles make a column there unsafe). Idempotent (if not exists).
- Server: an AccessCheck interface (allowed(userId) -> boolean) with a Supabase implementation using the service-role client and an in-memory implementation for development and tests. In production the assistant is configured only when the existing four variables are set (unchanged); access is checked per request.
- POST /api/ask: after the token is verified and before the cache lookup, the rate limit or any model call, reject a user without access with 403 and code not_enabled, message "The study assistant is by invitation for now." A cache hit must not bypass the check.
- GET /api/ask: when called with a valid bearer token, also return enabled: boolean so Today can show the right state before anyone asks. Without a token it stays as today.
- Development: ASSISTANT_ALLOW_ANONYMOUS=1 (non-production only) keeps working and skips the check. In development without the service-role key, an optional ASSISTANT_ALLOWED_EMAILS / ASSISTANT_ALLOWED_USER_IDS is NOT needed; the memory check allows everyone in development only. Production never falls back to allowing everyone: if the access lookup errors, deny (fail closed) and log the error name only.
- UI: a signed-in reader without access sees one calm line in the assistant panel, "The study assistant is by invitation for now.", and no prompts or question field. No pills or boxes; follow the sage design rules in docs/gatework/tasks/BJ-9.md.
- README: how the owner grants and removes access in the Supabase SQL editor, with the exact statements (insert by email via auth.users, delete by email, list who has access), and that the migration must be run first.

Out of scope: payments, an admin screen, gating anything other than the assistant, changes to sign-up.

Acceptance: unit tests cover allowed user, user without access (403, model not called, limiter not consumed, cache not served), access lookup error (denied), GET enabled true and false, dev anonymous mode; lint, typecheck, unit tests, build and Playwright pass with no environment variables.
